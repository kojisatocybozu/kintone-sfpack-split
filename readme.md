# kintone SFA Pack Customization

`kintone-sfpack-split`

kintone SFAパックの案件管理アプリおよび顧客管理アプリを対象としたJavaScriptカスタマイズプロジェクトです。

Viteによるバンドル、pnpmによるパッケージ管理、Kintone UI Component（KUC）によるUI構築を採用し、機能単位でソースコードを分割することで、保守性・拡張性の高い開発を目指します。

現在は **PoC（Proof of Concept）フェーズ** です。

---

## 1. プロジェクト概要

### 目的

本プロジェクトでは、主に以下の2つの機能を検証します。

**① 案件管理の担当者別提案明細管理**

案件管理アプリにおいて、顧客に紐づく複数の担当者を選択し、担当者ごとに提案商品・確度・商談フェーズを管理できるようにする。

**② 顧客管理の事業所階層・現場NG管理**

顧客管理アプリにおいて、本社と配下事業所の関係を管理し、本社で設定した「現場NG」を配下事業所へ連鎖反映する。

現場NGが設定された本社へのアプローチは可能とし、配下事業所への直接アプローチのみ禁止対象とする。

### 対象アプリ

| アプリ名 | App ID | 役割 |
|---|---:|---|
| 案件管理 | 941 | 案件情報・担当者・提案明細の管理 |
| 顧客管理 | 940 | 顧客情報・事業所階層・現場NGの管理 |
| 担当者管理 | 942 | 顧客に紐づく担当者情報の管理 |
| 活動履歴 | 939 | 案件・顧客の活動履歴 |

JavaScriptカスタマイズの直接対象は、案件管理（941）と顧客管理（940）です。

### アプリ間の関連

- 案件管理の「会社名」は顧客管理アプリを参照するルックアップフィールド。
- 案件管理の「顧客No_」と顧客管理の「顧客No」で顧客を識別する。
- 担当者管理の「顧客No_」によって顧客と担当者を関連付ける。
- 担当者管理の「担当者No_」を担当者の識別キーとして使用する。
- 現場NG情報は、案件管理側では標準ルックアップによる取得を基本方針とする。

## 4. Vite設定・ビルド構成

### 4.1 package.json

ES Modulesを使用するため、`type: module` を指定する。

主要なスクリプトは以下のとおり。

```json
{
  "type": "module",
  "scripts": {
    "dev": "vite build --watch --mode development",
    "build:deal": "vite build",
    "build:customer": "vite build --mode customer",
    "build": "pnpm run build:deal && pnpm run build:customer",
    "test": "vitest run",
    "test:watch": "vitest"
  }
}
```

### 4.2 vite.config.js

```javascript
import { defineConfig } from 'vite';

export default defineConfig(({ mode }) => {
  const isCustomer = mode === 'customer';

  return {
    build: {
      outDir: 'dist',
      emptyOutDir: !isCustomer,
      lib: {
        entry: isCustomer
          ? 'src/customerMain.js'
          : 'src/main.js',
        name: isCustomer
          ? 'CustomerCustomization'
          : 'SfpackCustomization',
        formats: ['iife'],
        fileName: () =>
          isCustomer
            ? 'customer-customization.js'
            : 'sfpack-customization.js',
      },
      minify: false,
      sourcemap: true,
    },
  };
});
```

kintoneに読み込ませるため、IIFE形式のJavaScriptを生成する。

### 4.3 アプリ別の出力

| 対象アプリ | エントリーポイント | 出力ファイル |
|---|---|---|
| 案件管理（941） | `src/main.js` | `sfpack-customization.js` |
| 顧客管理（940） | `src/customerMain.js` | `customer-customization.js` |

案件管理用CSSもビルド時に生成される場合があるため、実際の出力ファイル名を確認して登録する。

### 4.4 ビルドコマンド

両アプリをまとめてビルドする場合：

```powershell
pnpm run build
```

案件管理のみ：

```powershell
pnpm run build:deal
```

顧客管理のみ：

```powershell
pnpm run build:customer
```

現在のVite設定では、案件管理側のビルド時に `dist/` がクリアされます。

そのため、**両アプリの成果物を揃える場合は `pnpm run build` を使用する**ことを基本とします。

## 5. 担当者選択機能

### 概要

案件管理アプリで顧客を選択すると、担当者選択ボタンを表示する。

ボタンをクリックすると、担当者管理アプリから対象顧客の担当者を取得し、KUCのダイアログで複数選択できる。

1. 案件管理アプリで顧客を選択する。
2. 顧客Noを取得する。
3. 担当者選択ボタンを表示する。

5. KUC Dialog・Checkboxで担当者を選択する。
6. 選択した担当者を案件管理の「担当者テーブル」に登録する。

| 選択方式 | チェックボックス |
| UI | KUC |
| 担当者識別 | 担当者No_ |
| 登録先 | 担当者テーブル |
| 重複登録 | 防止 |
| 空行 | 除外 |

### 関連フィールド

案件管理アプリ：

| フィールド名 | フィールドコード |
|---|---|
| 会社名 | 会社名 |
| 顧客No | 顧客No_ |
| 担当者テーブル | 担当者テーブル |
| 担当者名 | 担当者 |
| 担当者No | 担当者No_ |

担当者管理アプリ：

| フィールド名 | フィールドコード |

| メールアドレス | メールアドレス |

## 6. 担当者別明細管理

### 概要

担当者ごとに独立した提案明細テーブルを使用する。

kintoneではJavaScriptからテーブルフィールド自体を動的生成できないため、事前に5つのテーブルを作成している。

### 明細テーブル

| テーブル | 対応担当者 |
|---|---|
| 担当者別明細01 | 1人目 |
| 担当者別明細02 | 2人目 |
| 担当者別明細03 | 3人目 |
| 担当者別明細04 | 4人目 |
| 担当者別明細05 | 5人目 |

各テーブルには次の3項目を設ける。

- 提案商品
- 確度
- 商談フェーズ

### 担当者との紐付け

各テーブルに対応する担当者No管理フィールドを設ける。

```text
明細担当者No_01
明細担当者No_02
明細担当者No_03
明細担当者No_04
明細担当者No_05
```

### データ管理方針

- 担当者Noをキーとして明細テーブルを割り当てる。
- 担当者の解除時も明細データは保持する。
- 同じ担当者を再追加した場合は以前の明細を復元する。
- 明細データが残っている枠を別担当者に自動再利用しない。
- 1人の担当者につき複数の提案明細を登録可能とする。

## 8. 顧客管理の事業所階層

### 概要

顧客管理アプリ（940）に、本社と配下事業所の関係を管理するフィールドを追加した。

### 階層管理フィールド

| フィールド名 | フィールドコード | 用途 |
|---|---|---|
| 事業所ID | `office_id` | 事業所を一意に識別するID |
| 本社の事業所ID | `honsha_office_id` | 所属する本社の事業所ID |
| 親事業所ID | `parent_office_id` | 直属の親事業所ID |

### 本社判定

本社レコードは、次の条件で判定する。

```javascript
office_id === honsha_office_id
```

ただし、両方のIDが設定されていることを前提とする。

本社自身の `honsha_office_id` には、自身の `office_id` を設定する。

### 階層構造の例

```text
本社100
├── 事業所200
│   └── 事業所300
└── 事業所400

本社800
└── 事業所900
```

`parent_office_id` は直属の親を示す。

一方、現場NGの連鎖更新では `parent_office_id` を辿らず、`honsha_office_id` が一致する事業所を対象とする。

### 現在の実装範囲

- 本社・配下事業所の識別：実装済み。
- 階層管理フィールドの追加：実施済み。
- 階層ツリーの画面表示：未実装。
- 階層構造の整合性チェック：今後検討。

## 9. 現場NG設定・連鎖更新機能

### 概要

顧客管理アプリ（940）において、本社で設定した現場NGを、同じ本社に属する配下事業所へ連鎖反映する。

**新仕様では、本社自身の現場NG判定は常に `OK` とし、現場NGが設定された本社の配下事業所のみ `NG` とする。**

### 関連フィールド

| フィールド名 | フィールドコード | フィールド種別 | 用途 |
|---|---|---|---|
| 現場NG設定 | `genba_ng` | チェックボックス | 本社が配下事業所へのアプローチ禁止を設定 |
| 現場NG判定 | `effective_genba_ng` | 文字列（1行） | 事業所ごとのアプローチ可否を保持 |

### 現場NG設定

`genba_ng` は本社で設定する管理用チェックボックス。

チェックボックスの選択肢：

```text
現場NG
```

- 本社：編集可能。
- 配下事業所：画面上では編集不可。

### 現場NG判定

`effective_genba_ng` は連鎖更新によって設定される、事業所ごとのアプローチ可否を示す判定値。

| 値 | 意味 |
|---|---|
| `NG` | この事業所への直接アプローチは禁止 |
| `OK` | この事業所へのアプローチは可能 |

本社自身は、`genba_ng` がONであっても `effective_genba_ng` を `OK` とする。

### 連鎖更新の条件

本社レコードの保存成功後、以下の条件に一致するレコードを取得する。

```text
honsha_office_id = 本社のoffice_id
```

対象には本社自身も含めるが、本社と配下事業所で設定する判定値を区別する。

### 連鎖更新の動作

| 本社の現場NG設定 | 本社の現場NG判定 | 配下事業所の現場NG判定 |
|---|---|---|
| ON | `OK` | `NG` |
| OFF | `OK` | `OK` |

ONとOFFの両方向に連鎖更新する。

### 更新処理

- kintone REST APIを使用する。
- 対象レコードをページングして取得する。
- 複数レコード更新APIを使用する。
- 1回の更新リクエストは最大100件とする。
- 本社自身は常に `OK` に更新する。
- 配下事業所は本社の現場NG設定に従って `NG` または `OK` に更新する。
- 更新件数とエラー情報をコンソールへ出力する。
- 本社の詳細画面に手動再同期ボタンを設置する。

### 手動再同期

本社の詳細画面には、次のボタンを表示する。

```text
現場NG判定を再同期
```

ボタンを押すと、現在の本社の現場NG設定を基準として、本社自身と配下事業所の判定を再更新する。

現在のHTMLボタンをKUC Buttonへ置き換えることも可能であり、KUC対応はコード反映状況を確認して完了扱いとする。

### 新仕様の検証ケース

| 操作 | 本社 | 配下事業所 |
|---|---|---|
| 本社100でON | 100 → OK | 200・300・400 → NG |
| 本社100でOFF | 100 → OK | 200・300・400 → OK |
| 本社800でON | 800 → OK | 900 → NG |
| 本社800でOFF | 800 → OK | 900 → OK |

※ 旧仕様での連鎖更新は動作確認済み。新仕様については、コード反映後に再同期と動作確認を行う。

## 10. 現場NG警告表示機能

### 概要

顧客管理アプリ（940）の一覧画面および詳細画面で、アプローチ禁止対象となる事業所に警告を表示する。

### 重要な業務ルール

**本社はアプローチ可能とし、現場NG設定された本社の配下事業所のみアプローチ禁止とする。**

### 警告表示条件

新仕様では、現場NG判定が `NG` の事業所をアプローチ禁止対象とする。

```javascript
effective_genba_ng === 'NG'
```

ただし、現行の `customerNgWarning.js` では、本社に誤った警告を表示しないため、事業所IDと本社IDを比較する追加条件も設けている。

```javascript
effective_genba_ng === 'NG'
  && office_id !== honsha_office_id
```

この追加条件は現時点では維持する。

また、IDが未設定で現場NG判定が `NG` の場合は、安全側の表示として警告対象とする。

### 判定例

| 事業所 | 本社／配下 | 現場NG判定 | 警告 |
|---|---|---|---|
| 100 | 本社 | OK | 表示しない |
| 200 | 配下 | NG | 表示する |
| 300 | 配下 | NG | 表示する |
| 400 | 配下 | NG | 表示する |
| 500 | 本社 | OK | 表示しない |
| 800 | 本社 | OK | 表示しない |
| 900 | 配下 | NG | 表示する |

### 詳細画面

アプローチ禁止対象の事業所では、警告メッセージを表示する。

```text
現場NG：この事業所への直接アプローチは禁止されています。
本社または担当窓口へ確認してください。
```

本社レコードには警告を表示しない。

### 一覧画面

- 現在表示中のレコードに含まれるアプローチ禁止対象の件数を表示する。
- 対象行を強調表示する。
- 本社は警告件数・行強調の対象から除外する。

### 技術上の注意

一覧画面の行強調は、kintone標準一覧のHTML構造に依存するPoC実装である。

標準一覧のDOM構造が変更された場合は、修正が必要になる可能性がある。

また、一覧画面の件数は現在表示中のレコードに対する件数であり、全顧客のNG件数ではない。

## 11. 案件管理での現場NG情報の利用

### 基本方針

案件管理アプリ（941）では、現場NG情報の取得に **kintone標準のルックアップ機能** を利用する。

現場NGのための追加JavaScriptカスタマイズは、現時点では行わない。

### 取得する情報

| 顧客管理フィールド | 用途 |
|---|---|
| `effective_genba_ng` | 事業所ごとのアプローチ可否 |
| `genba_ng` | 本社での現場NG設定状態（必要に応じて取得） |

### アプローチ禁止の判定

案件管理では、ルックアップで取得した「現場NG判定」の値によって判断する。

| 現場NG判定 | 判定 |
|---|---|
| `NG` | アプローチ禁止 |
| `OK` | アプローチ可能 |
| 空欄 | 要確認 |

本社自身は常に `OK` となるため、正常に同期されたデータでは、案件管理側で本社・配下事業所を判別する追加ロジックは不要とする。

### 注意事項

標準ルックアップでコピーした値は、参照元の顧客管理レコードが更新されても、既存の案件管理レコードへ自動反映されない。

そのため、現場NG設定変更後の既存案件への反映方法は、今後の運用検討事項とする。

また、現場NG判定が空欄の場合は `OK` と同一視せず、データ確認または再同期の対象とする。

## 12. KUC（kintone UI Component）

UIはkintone標準画面との統一性を重視し、必要に応じてKUCを使用する。

| コンポーネント | 用途 | 状態 |
|---|---|---|
| Dialog | 担当者選択画面 | 実装済み |
| Checkbox | 担当者の複数選択 | 実装済み |
| Button | 案件管理の操作ボタン | 利用中・個別の実装確認対象 |
| Button | 現場NG判定の再同期 | KUC対応検討中 |

案件管理および顧客管理アプリのフィールド定義・レイアウトは、kintone REST APIを利用して取得・変更する。

### プレビュー環境のAPI

```text

```

レイアウト：

```text

```

```text
POST /k/v1/preview/app/form/fields.json
```

レイアウト変更：

```text
PUT /k/v1/preview/app/form/layout.json
```


### 運用上の注意

- フィールド定義やレイアウトを変更する場合は、既存設定をバックアップする。
- アプリ設定変更後は、適切なタイミングでアプリを更新する。
- PoC環境と本番環境を混同しない。
- REST APIでのレコード更新には、実行ユーザーの権限が必要となる。

## 18. 現時点の制約・注意事項

### 18.1 現場NG連鎖更新の非同期処理

本社レコード保存後の連鎖更新は、REST APIによる別処理である。

本社レコードの保存と、配下事業所への連鎖更新は単一トランザクションではない。

そのため、以下の可能性がある。

- 保存後の画面遷移による通信中断。
- APIエラーによる更新失敗。
- 一部のレコードのみ更新される状態。
- レコード更新権限不足による失敗。

手動再同期機能は用意しているが、すべての更新が必ず完了することを保証するものではない。

### 18.2 編集制限

本社以外の `genba_ng` の編集制限と、`effective_genba_ng` の編集制限はJavaScriptによる画面制御である。

REST APIなどを通じた直接変更を完全に禁止するものではない。

本番運用では、アクセス権設定やサーバー側の更新制御を検討する。

### 18.3 階層変更時の整合性

事業所の本社IDや親事業所IDを変更した場合、旧所属グループの再計算や整合性チェックは自動実行していない。

階層変更時の再同期ルールは今後の検討事項とする。

### 18.4 一覧画面のDOM依存

現場NG対象行の強調表示は、kintone標準一覧のHTML構造に依存する。

kintoneの画面仕様変更により、動作しなくなる可能性がある。

### 18.5 ルックアップ値の更新

標準ルックアップでコピーした値は、参照元の変更によって自動更新されない。

既存案件に最新の現場NG情報を反映する方法は、今後検討する。

### 18.6 担当者別明細のデータ保持

担当者を選択解除した場合、対応する明細テーブルを非表示にするが、データは保持する。

コピー先に既存データがある場合は、上書きせずスキップする。

これらはPoCで採用した暫定仕様であり、本番運用前に再評価する。

### 18.7 新仕様への移行

旧仕様では、本社自身の `effective_genba_ng` にも `NG` を設定していた。

新仕様では、本社自身の判定を常に `OK` とする。

そのため、コード変更後には以下を実施する。

1. 顧客管理用JavaScriptを再ビルドする。
2. 顧客管理アプリに新しいJavaScriptを適用する。
3. 本社100・本社800など、既存の本社レコードで手動再同期を実行する。
4. 本社の判定が `OK` となることを確認する。
5. 配下事業所の判定が本社の現場NG設定に従うことを確認する。
6. 一覧・詳細画面の警告表示を再確認する。

## 20. 開発上の基本方針

本プロジェクトでは、以下を重視する。

- 機能ごとにソースコードを分割する。
- アプリごとにビルド成果物を分離する。
- フィールドコードは設定モジュールで管理する方針とする。
- API処理とUI処理を分離する。
- 必要に応じてKUCを使用する。
- kintone標準機能で対応できる部分は標準機能を優先する。
- kintone標準のデータ保存機構を利用する。
- 既存データを不用意に削除・変更しない。
- 開発・検証は動作テスト環境で行う。
- GitHubで変更履歴を管理する。
- PoCで確認できた機能と、本番運用で必要な品質要件を区別する。

**本プロジェクトは、PoCを通じて実用性を検証しながら、段階的に機能と品質を高めていく。**
