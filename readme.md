# kintone SFA Pack Customization

`kintone-sfpack-split`

kintone SFAパックの案件管理アプリおよび顧客管理アプリを対象としたJavaScript・サンプルカスタマイズプロジェクトです。

Viteによるバンドル、pnpmによるパッケージ管理、Kintone UI Component（KUC）によるUI構築を採用し、機能単位でソースコードを分割することで、保守性・拡張性の高い開発を目指します。

---

## 1. プロジェクト概要

### 目的

本プロジェクトでは、主に以下の2つの機能を検証します。

**① 案件管理の担当者別提案明細管理**

案件管理アプリで顧客に紐づく複数の担当者を選択し、担当者ごとに提案商品・確度・商談フェーズを管理します。

**② 顧客管理の事業所階層・現場NG管理**

顧客管理アプリで本社と配下事業所の関係を管理し、本社で設定した「現場NG」を配下事業所へ連鎖反映します。本社自身はアプローチ可能とし、現場NGが設定された本社の配下事業所のみを直接アプローチ禁止とします。

### 対象アプリ

| アプリ名 | ステージング App ID | 役割 |
|---|---:|---|
| 案件管理 | 941 | 案件情報・担当者・提案明細の管理 |
| 顧客管理 | 940 | 顧客情報・事業所階層・現場NGの管理 |
| 担当者管理 | 942 | 顧客に紐づく担当者情報の管理 |
| 活動履歴 | 939 | 案件・顧客の活動履歴 |

※ 上記IDは現在のステージング環境の値です。環境によってアプリIDが異なる場合があります。

JavaScriptカスタマイズの直接対象は、案件管理と顧客管理です。

### アプリ間の関連

- 案件管理の「会社名」は顧客管理アプリを参照するルックアップフィールド。
- 案件管理の「顧客No_」と顧客管理の「顧客No」で顧客を識別する。
- 担当者管理の「顧客No_」によって顧客と担当者を関連付ける。
- 担当者管理の「担当者No_」を担当者の識別キーとして使用する。
- 案件管理では、現場NG判定を標準ルックアップで取得する方針とし、現場NG表示のための独自JavaScriptは実装しない。

## 4. Vite設定・ビルド構成

### 4.1 package.json

ES Modulesを使用するため、`type: module` を指定します。主要なスクリプトは以下のとおりです。

```json
{
  "type": "module",
  "scripts": {
    "dev": "vite build --watch --mode development",
    "build:deal": "vite build",
    "build:customer": "vite build --mode customer",
    "build": "pnpm run build:deal && pnpm run build:customer",
    "test": "vitest run",
    "test:watch": "vitest"
  }
}
```

### 4.2 vite.config.js

```javascript
import { defineConfig } from 'vite';

export default defineConfig(({ mode }) => {
  const isCustomer = mode === 'customer';

  return {
    build: {
      outDir: 'dist',
      emptyOutDir: !isCustomer,
      lib: {
        entry: isCustomer
          ? 'src/customerMain.js'
          : 'src/main.js',
        name: isCustomer
          ? 'CustomerCustomization'
          : 'SfpackCustomization',
        formats: ['iife'],
        fileName: () =>
          isCustomer
            ? 'customer-customization.js'
            : 'sfpack-customization.js',
      },
      minify: false,
      sourcemap: true,
    },
  };
});
```

kintoneに読み込ませるため、IIFE形式のJavaScriptを生成します。

### 4.3 アプリ別の出力

| 対象アプリ | エントリーポイント | 出力ファイル |
|---|---|---|
| 案件管理 | `src/main.js` | `sfpack-customization.js` |
| 顧客管理 | `src/customerMain.js` | `customer-customization.js` |

### 4.4 ビルドコマンド

両アプリをまとめてビルド：

```powershell
pnpm run build
```

案件管理のみ：

```powershell
pnpm run build:deal
```

顧客管理のみ：

```powershell
pnpm run build:customer
```

現在のVite設定では、案件管理側のビルド時に `dist/` がクリアされます。そのため、両アプリの成果物を揃える場合は `pnpm run build` を使用します。

### 処理フロー

1. 案件管理アプリで顧客を選択する。

3. 担当者選択ボタンを表示する。

5. KUC Dialog・Checkboxで担当者を選択する。
6. 選択した担当者を案件管理の「担当者テーブル」に登録する。

| UI | KUC |
| 担当者識別 | 担当者No_ |
| 登録先 | 担当者テーブル |
| 重複登録 | 防止 |
| 空行 | 除外 |

### 関連フィールド

案件管理アプリ：

| フィールド名 | フィールドコード |

| 会社名 | 会社名 |
| 顧客No | 顧客No_ |

## 6. 担当者別明細管理

### 概要

担当者ごとに独立した提案明細テーブルを使用します。kintoneではJavaScriptからテーブルフィールド自体を動的生成できないため、事前に5つのテーブルを作成しています。

### 明細テーブル

| テーブル | 対応担当者 |
|---|---|
| 担当者別明細01 | 1人目 |
| 担当者別明細02 | 2人目 |
| 担当者別明細03 | 3人目 |
| 担当者別明細04 | 4人目 |
| 担当者別明細05 | 5人目 |

各テーブルには次の3項目を設けます。

- 提案商品
- 確度
- 商談フェーズ

### 担当者との紐付け

各テーブルに対応する担当者No管理フィールドを設けます。

```text
明細担当者No_01
明細担当者No_02
明細担当者No_03
明細担当者No_04
明細担当者No_05
```

### データ管理方針

- 担当者Noをキーとして明細テーブルを割り当てる。
- 担当者の解除時も明細データは保持する。
- 同じ担当者を再追加した場合は以前の明細を復元する。
- 明細データが残っている枠を別担当者に自動再利用しない。
- 1人の担当者につき複数の提案明細を登録可能とする。

## 7. 担当者別明細コピー機能

### 概要

案件管理アプリで、共通明細テーブルから担当者別明細テーブルへデータをコピーする機能です。

### 現在の仕様

- 共通明細の有効な行をコピー元とする。
- 選択中の担当者に対応する担当者別明細をコピー先とする。
- コピー先に既存の入力済み明細がある場合は、上書きせずスキップする。
- コピー先の既存データを不用意に削除しない。
- コピー後の保存・再編集を含めて動作確認済み。

### コピー処理の考え方

1. コピー元テーブルから入力済みの行を抽出する。
2. コピー元とコピー先のフィールドコードを対応付ける。
3. コピー先のフィールドコードに合わせて新しい行オブジェクトを生成する。
4. kintoneのレコード画面に反映し、利用者がレコードを保存する。

テーブル行のIDはコピー先へ引き継がず、新規行として作成します。

### 今後の検討事項

- コピー先にデータが存在する場合の上書き・追記ルール。
- コピー結果やスキップ理由の表示改善。
- 担当者解除後の明細データ保持との整合性。

## 8. 顧客管理の事業所階層

### 概要

顧客管理アプリに、本社と配下事業所の関係を管理するフィールドを追加しています。

### 階層管理フィールド

| フィールド名 | フィールドコード | 用途 |
|---|---|---|
| 事業所ID | `office_id` | 事業所を一意に識別するID |
| 本社の事業所ID | `honsha_office_id` | 所属する本社の事業所ID |
| 親事業所ID | `parent_office_id` | 直属の親事業所ID |

### 本社判定

本社レコードは、事業所IDと本社の事業所IDが一致するレコードです。

```javascript
office_id === honsha_office_id
```

本社自身の `honsha_office_id` には、自身の `office_id` を設定します。

### 階層構造の例

```text
本社100
├── 事業所200
│   └── 事業所300
└── 事業所400

本社800
└── 事業所900
```

`parent_office_id` は直属の親を示します。一方、現場NGの連鎖更新では `parent_office_id` を再帰的に辿らず、`honsha_office_id` が一致する事業所を検索対象とします。

### 現在の実装範囲

- 本社・配下事業所の識別：実装済み。
- 階層管理フィールドの追加：実施済み。
- 階層ツリーの画面表示：未実装。
- 階層構造の整合性チェック：今後検討。

## 9. 現場NG設定・連鎖更新機能

### 概要

顧客管理アプリにおいて、本社で設定した現場NGを、同じ本社に属する配下事業所へ連鎖反映します。

**本社自身の現場NG判定は常に `OK` とし、現場NGが設定された本社の配下事業所のみ `NG` とします。**

### 関連フィールド

| フィールド名 | フィールドコード | フィールド種別 | 用途 |
|---|---|---|---|
| 現場NG設定 | `genba_ng` | チェックボックス | 本社が配下事業所へのアプローチ禁止を設定 |
| 現場NG判定 | `effective_genba_ng` | 文字列（1行） | 事業所ごとのアプローチ可否を保持 |

### 現場NG設定

`genba_ng` は本社で設定する管理用チェックボックスです。選択肢は `現場NG` です。

- 本社：編集可能。
- 配下事業所：画面上では編集不可。

### 現場NG判定

`effective_genba_ng` は連鎖更新によって設定される、事業所ごとのアプローチ可否を示す判定値です。

| 値 | 意味 |
|---|---|
| `NG` | この事業所への直接アプローチは禁止 |
| `OK` | この事業所へのアプローチは可能 |

本社自身は、`genba_ng` がONであっても `effective_genba_ng` を `OK` とします。

### 連鎖更新の条件

本社レコードの保存成功後、以下の条件に一致するレコードを検索します。

```text
honsha_office_id = 本社のoffice_id
```

検索対象には本社自身も含めますが、本社と配下事業所で設定する判定値を区別します。

### 連鎖更新の動作

| 本社の現場NG設定 | 本社の現場NG判定 | 配下事業所の現場NG判定 |
|---|---|---|
| ON | `OK` | `NG` |
| OFF | `OK` | `OK` |

ONとOFFの両方向に連鎖更新します。

### 更新処理

- kintone REST APIを使用する。
- 対象レコードをページングして取得する。
- 複数レコード更新APIを使用する。
- 1回の更新リクエストは最大100件とする。
- 本社自身は常に `OK` に更新する。
- 配下事業所は本社の現場NG設定に従って `NG` または `OK` に更新する。
- 更新件数とエラー情報をコンソールへ出力する。
- 本社の詳細画面に手動再同期ボタンを設置する。

### 手動再同期

本社の詳細画面には「現場NG判定を再同期」ボタンを表示します。ボタンを押すと、現在の本社の現場NG設定を基準として、本社自身と配下事業所の判定を再更新します。

### 検証ケース

| 操作 | 本社 | 配下事業所 |
|---|---|---|
| 本社100でON | 100 → OK | 200・300・400 → NG |
| 本社100でOFF | 100 → OK | 200・300・400 → OK |
| 本社800でON | 800 → OK | 900 → NG |
| 本社800でOFF | 800 → OK | 900 → OK |

上記のON/OFF連鎖更新および複数の本社グループでの動作を確認しています。

## 10. 現場NGの視覚的な識別

### 基本方針

現場NG対象の視覚的な強調表示は、独自JavaScriptではなく、条件書式プラグイン等の利用を優先します。

判定には顧客管理アプリの `effective_genba_ng` を使用します。

```text
effective_genba_ng = NG
```

本社自身は常に `OK` となるため、配下事業所のみを強調表示する運用とします。

### JavaScriptによる警告表示を採用しない理由

- 値に応じた背景色・文字色などの条件付き表示は、条件書式プラグインで実現できる可能性がある。
- 標準機能やプラグインで対応できる表示処理を独自JavaScriptで重複実装しない。
- JavaScriptは本社から配下事業所への連鎖更新など、独自の業務ロジックに集中させる。

※ 利用するプラグインの対応画面・条件設定・ライセンス・保守条件は、導入前に確認します。

## 11. 案件管理での現場NG情報の利用

### 基本方針

案件管理アプリでは、現場NG情報の取得にkintone標準のルックアップ機能を利用します。現場NG判定のための追加JavaScriptカスタマイズは行わない方針です。

### 取得する情報

| 顧客管理フィールド | 用途 |
|---|---|
| `effective_genba_ng` | 事業所ごとのアプローチ可否 |
| `genba_ng` | 本社での現場NG設定状態（必要に応じて取得） |

### アプローチ可否の判断

| 現場NG判定 | 判定 |
|---|---|
| `NG` | アプローチ禁止 |
| `OK` | アプローチ可能 |
| 空欄 | 要確認 |

本社自身は常に `OK` となるため、正常に同期されたデータでは、案件管理側で本社・配下事業所を判別する追加ロジックは不要です。

### 注意事項

標準ルックアップでコピーした値は、参照元の顧客管理レコードが更新されても、既存の案件管理レコードへ自動反映されません。現場NG設定変更後の既存案件への反映方法は、今後の運用検討事項です。

現場NG判定が空欄の場合は `OK` と同一視せず、データ確認または再取得の対象とします。

## 13. 環境別設定・ローカル開発手順

### 13.1 環境別設定

案件管理アプリから参照する担当者管理アプリのIDは、環境によって異なる可能性があるため、環境別設定ファイルで管理します。

```text
src/config/
├── fields.js
├── staging.js
└── production.js
```

ステージング環境では `staging.js`、本番環境では `production.js` を読み込みます。

例：

```javascript
// staging.js（例）
window.SFPACK_CONFIG = Object.freeze({
  contactAppId: 942,
});
```

本番用ファイルには、本番環境の担当者管理アプリIDを設定します。

環境別設定ファイルはViteのバンドルに含めず、案件管理アプリのJavaScriptカスタマイズ設定で、共通バンドルより先に読み込みます。

### 13.2 依存パッケージのインストール

```powershell
pnpm install
```

## 14. kintoneへの適用

### PoC期間

- kintoneの動作テスト環境を使用する。
- JavaScriptはLive ServerのローカルHTTPS URLから読み込む。
- 案件管理と顧客管理で別々のJavaScriptを登録する。
- 案件管理では環境別設定ファイルを共通バンドルより先に登録する。
- フィールド設定は必要に応じてREST APIを利用して管理する。
- 本番環境への反映は行わない。

### アプリ別の登録

| アプリ | 登録するJavaScript |
|---|---|
| 案件管理 | 環境別 `staging.js` または `production.js` → `sfpack-customization.js` |
| 顧客管理 | `customer-customization.js` |

案件管理の独自CSSは、必要に応じて別途登録します。

### 本番リリース時

1. Viteで本番用ビルドを実行する。
2. 生成されたJavaScript・必要なCSSをkintoneに登録する。
3. 案件管理には本番用 `production.js` を共通バンドルより先に登録する。
4. 動作テスト環境で最終確認する。
5. アプリ設定を運用環境へ反映する。

本番環境にはlocalhostや127.0.0.1のURLを設定しません。

## 15. フォーム設定の管理

案件管理および顧客管理アプリのフィールド定義・レイアウトは、kintone REST APIを利用して取得・変更します。

### プレビュー環境のAPI

フィールド一覧：

```text
GET /k/v1/preview/app/form/fields.json
```

レイアウト：

```text
GET /k/v1/preview/app/form/layout.json
```

フィールド追加：

```text
POST /k/v1/preview/app/form/fields.json
```

レイアウト変更：

```text
PUT /k/v1/preview/app/form/layout.json
```

アプリ設定の運用環境への反映：

```text
POST /k/v1/preview/app/deploy.json
```

### フィールド追加用スクリプト

案件管理：

```text
scripts/add-deal-proposal-fields.js
```

顧客管理：

```text
add-customer-hierarchy-fields.js
```

顧客管理では、事業所階層・現場NG関連の5フィールドを追加しています。

### 運用上の注意

- フィールド定義やレイアウトを変更する場合は、既存設定をバックアップする。
- アプリ設定変更後は、適切なタイミングでアプリを更新する。
- PoC環境と本番環境を混同しない。
- REST APIでのレコード更新には、実行ユーザーの権限が必要となる。

## 18. 現時点の制約・注意事項

### 18.1 現場NG連鎖更新の非同期処理

本社レコード保存後の連鎖更新はREST APIによる別処理です。本社レコードの保存と配下事業所への連鎖更新は単一トランザクションではありません。

そのため、以下の可能性があります。

- 保存後の画面遷移による通信中断。
- APIエラーによる更新失敗。
- 一部のレコードのみ更新される状態。
- レコード更新権限不足による失敗。

手動再同期機能は用意していますが、すべての更新が必ず完了することを保証するものではありません。

### 18.2 編集制限

本社以外の `genba_ng` の編集制限と、`effective_genba_ng` の編集制限はJavaScriptによる画面制御です。REST APIなどを通じた直接変更を完全に禁止するものではありません。

本番運用では、アクセス権設定や更新経路の制御を検討します。

### 18.3 階層変更時の整合性

事業所の本社IDや親事業所IDを変更した場合、旧所属グループの再計算や整合性チェックは自動実行していません。階層変更時の再同期ルールは今後の検討事項です。

### 18.4 ルックアップ値の更新

標準ルックアップでコピーした値は、参照元の変更によって既存の案件管理レコードへ自動反映されません。現場NG設定変更後の既存案件への反映方法は、今後の運用検討事項です。

### 18.5 担当者別明細のデータ保持

担当者を選択解除した場合、対応する明細テーブルを非表示にしますが、データは保持します。コピー先に既存データがある場合は、上書きせずスキップします。

これらはPoCで採用した暫定仕様であり、本番運用前に再評価します。

### 18.6 セキュリティ・保守

- 画面上の `disabled` は、REST API等からの更新を禁止するアクセス権制御の代替ではありません。
- APIトークンやパスワードなどの秘密情報をソースコードや環境別設定ファイルに記載しません。
- 外部ライブラリはpnpmのlockファイルでバージョンを管理し、定期的な脆弱性確認を行います。
- 本番適用前に、利用者権限・API実行権限・更新失敗時の運用を確認します。

## 20. 開発上の基本方針

本プロジェクトでは、以下を重視します。

- 機能ごとにソースコードを分割する。
- アプリごとにビルド成果物を分離する。
- 環境依存の設定値は環境別設定ファイルに分離する。
- フィールドコードは設定モジュールで管理する。
- API処理とUI処理を分離する。
- 必要に応じてKUCを使用する。
- kintone標準機能やプラグインで対応できる部分は標準機能・プラグインを優先する。
- kintone標準のデータ保存機構を利用する。
- 既存データを不用意に削除・変更しない。
- 開発・検証は動作テスト環境で行う。
- GitHubで変更履歴を管理する。
- PoCで確認できた機能と、本番運用で必要な品質要件を区別する。

**本プロジェクトは、PoCを通じて実用性を検証しながら、段階的に機能と品質を高めていきます。**
